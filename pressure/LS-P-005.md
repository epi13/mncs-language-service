# LS-P-005 — JSON-RPC/LSP framing must remain a Rust boundary

Status: REJECTED-AS-PRESSURE

## Investigation

A full MNCS-native LSP transport would require, at minimum: string
literals and text manipulation (URIs, JSON keys), JSON parsing and
serialization (optional fields, unions, recursive structures, request
IDs), and stdio/socket I/O with framing (`Content-Length` headers).

## Reproducer

Attempting to model even one LSP message (`textDocument/didOpen`) in MNCS
fails at the first field: URIs and method names are strings, and MNCS has
no string type or literal (see LS-P-002). There is likewise no socket,
stdio, or buffered-I/O surface in the language.

## Reasoning

This is an accepted bootstrap boundary, not a deficiency to repair. Every
language needs a host I/O and transport substrate; LSP framing is
operating-system integration in the same class as networking and process
management, which the campaign brief itself lists as legitimate Rust-side
responsibilities. The service keeps this boundary minimal and explicit:
`crates/lsp` owns JSON-RPC framing and protocol translation only, and all
semantic answers come from the protocol-neutral core that MNCS-native
kernels already query differentially.

Revisit only if MNCS gains a string/JSON story for other reasons; do not
add transport-shaped features to the language to serve this record.
