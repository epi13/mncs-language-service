# LS-P-006 — Bounded symbol filtering via generic stdlib execution

Status: VERIFIED

## Original pressure (roadmap item (a))

The ROADMAP's next evidence-led pressure point was "bounded symbol
filtering": can MNCS express a service-style filter over a bounded
collection through the authoritative standard library, executed on a real
backend, with the result trusted differentially?

## Resolution

Yes. `mncs/filter_query.mncs` adapts the authoritative generic
`mncs.core.sequences.v1::count<N: Nat>` to a fixed 8-slot service
envelope with explicit instantiation (`count<8>(tags, wanted)`), and
`crates/service-core/src/native_filter.rs` executes it on the
`mncs-research-bytecode` backend with fail-closed differential comparison
against the Rust control.

## Verification

- `crates/service-core/tests/native_filter.rs`: differential agreement on
  a multi-kind probe document plus kernel-artifact reuse across calls.
- `crates/mcp/tests/mcp_protocol.rs::native_kind_count_executes_through_the_real_tool_surface`:
  end-to-end through the agent tool surface, including fail-closed
  behavior on unknown kind names.
- No `mncs-language` change was required: explicit generic instantiation,
  bounded `[i64; N]` sequences, cross-module `use` resolution, and
  research-bytecode execution of generic stdlib functions all worked as
  specified on the first attempt.

## Remaining boundary (see LS-P-002)

The kernel counts integer kind-tags, not names: projecting names into
MNCS is still impossible without strings. That restriction is tracked
separately and does not reopen this record.
