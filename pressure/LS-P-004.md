# LS-P-004 — No cancellation: analysis is synchronous and uninterruptible

Status: CONFIRMED

## 1. Reasonable service requirement

LSP clients cancel stale requests (`$/cancelRequest`) and mutate documents
while analysis is in flight. The service must be able to abandon a
superseded analysis instead of finishing work nobody will read.

## 2. Natural MNCS expression

N/A — this is a host-contract gap, not a language expression gap. The
natural shape would be a cancellation token or fuel-bounded frontend entry
point the service can poll or drop.

## 3. What prevents it

`ReferenceCompiler::front_end_with_resolver` runs to completion
synchronously with no cancellation hook. The service serializes duplicate
work with per-document mutexes and detects staleness only *after* analysis
publishes (fingerprint comparison in `snapshot()`), so a superseded edit
still pays the full pipeline cost of the abandoned state.

## 4. Minimal reproducer

Two rapid sequential edits: the first analysis runs to completion even
though its result is discarded unpublished when the second edit lands
mid-flight (observable in `snapshot()`: the publish guard compares
fingerprints after the frontend returns, never during).

## 5. Expected behavior

A cancelled request stops consuming CPU promptly (token,Generation check,
or bounded-chunk API).

## 6. Actual behavior

Correct but wasteful: results are never wrong (stale snapshots are never
published), but tail latency under fast typing is the full pipeline cost
per keystroke with no way to shed load.

## 7. Classification

Compiler/service contract. Severity: low today (~16ms cold analyses fit
inside human typing latency), high if files or elaboration costs grow.

## 8. Workaround

Post-hoc staleness guards (publish only when the fingerprint still
matches), per-document locks (no duplicate work for the same state),
cheap resident queries (no re-analysis for navigation). No load-shedding.

## 9. Cost of the workaround

Under sustained fast typing the server does strictly more work than
necessary; no architectural seam exists yet for cooperative cancellation.
Pairs with LS-P-001: incrementality reduces the need, cancellation bounds
the worst case.
